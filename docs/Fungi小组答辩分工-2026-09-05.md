## 你 —— 项目定位、总体架构与网络通讯拓扑

**开场白（1 分钟，把分量立住）**
"这个项目从零到发布由我主导设计与实现：三代 harness 的演进（Psi → YESIR → Fungi）、TriLayer 编排、星型拓扑网络协议、全部前后端代码、267 个测试和 CI/CD。我先讲清楚网络这一层为什么这样设计。"

**讲稿要点**
1. **动机**：一个进程里的 Orchestrator 再强也只在一台机器上。Fungi 把 Orchestrator 撒到 LAN 每台主机，让它们彼此成为工具。
2. **星型拓扑，server relay**：一台主机 `--server` 起房，承载 HTTP hub（名册 / 消息中转 / 未决同意 / 数据存储）；其余 `--join` 直连。**clone 间流量全部经 server 投递**——不做 P2P 网状，因为裁决、存储、消息可靠性只需要收敛在一个点。
3. **投递语义**：一切皆消息信封（envelope）；at-least-once 投递 + 消息 id 去重；心跳保活，断线重连后重放未决内容。
4. **克制**：无 Redis 等协调设施、通讯 clone 拿不到原生 bash/read/write——引用 Around 的教训"先写 spec 再动手"。
5. 现场组一次真房间（你起房，A 用 Token 加入），把话筒交给 A。

**可能被问**
- "为什么星型不是网状？"→ 网状要解决一致性和路由，房间场景一个 hub 足够，且同意裁决天然需要中立第三方（server）。
- "server 挂了怎么办？"→ 房间即 server 所在主机，属单点；这是 v1 的已知边界（LAN 内、明文 HTTP、无传输加密，token 鉴权）。

## 组员 A —— TriLayer 分层与工具系统

**开场白（30 秒）**
"我讲的是 Fungi 里 AI 的'组织架构'：三层分派怎么工作，以及不同身份的 AI 分别能碰到哪些工具。"

**讲稿要点**
1. **三层**：L1 Orchestrator（**唯一**与用户对话的层，唯一能 inquire）→ 用 `spawn` 拆出 L2 Task Agent → 再拆 L3 Worker。每轮最多 8 次 spawn，L3 到底。
2. **派发契约 TaskSpec**：上层必须写清 `goal`（自包含目标，不许引用上下文）+ `reply_format`（汇报格式，如"yes/no 加理由"、"含 X/Y 字段的 JSON"）；下层严格在范围内执行，答案作为 spawn 的工具结果原路返回。
3. **工具面（两个维度）**：
   - 按功能：文件（files）、搜索（search）、shell、web、MCP 扩展、ask；
   - 按身份：**本机 clone**（local）有原生全套 + `delegate`（跨主机委派）；**通讯 clone**（comm）只有守卫版文件工具 + `send_peer` / `confirm` / `inquire`——**没有 bash/read/write**，因为它的地盘在别人主机上。
4. **为什么这样设计**：分层防止"一个 AI 什么都自己干"，权限面按身份收缩——能力越大、离用户越近，工具越多。

**演示脚本**
1. 两台真机组好房间（你已起房）。
2. 演示 `send_peer`：两台主机的通讯 clone 自由互发消息（注意：**不自动回信**，LLM 想回才显式调 send_peer——这是刻意的克制设计）。
3. 演示 `delegate`：在主机 A 让本机 clone 委派主机 B 完成一个小任务并按 reply_format 回报。

**可能被问**
- "spawn 和 delegate 什么区别？"→ spawn 是**同主机**向下分层派发；delegate 是**跨主机**委派另一台的本机 clone。
- "为什么通讯 clone 不能跑命令？"→ 最小权限：它操作的是别人主机，能做的事全部要过守卫和同意。

## 组员 B —— GUI 启动器与托盘体验

**开场白（30 秒）**
"我演示的是普通用户看到的 Fungi：从双击启动到进房间、到关窗后台驻留的全流程。"

**演示脚本**
1. `python start.py`：启动器界面——发起房间 / 加入房间 / 打开 WebUI / 模型配置 / 帮助。
2. **Token 自定义**：在发起按钮上方输入框改 Token（字母数字，1-64 位）→ 按回车生效；强调"运行中改完回车立即热更新，老朋友要用新 Token 重进"——等于换锁防蹭房。
3. 组好房间后**关窗** → 提示"Fungi 已转入托盘"，房间继续跑；托盘右键菜单演示。
4. **单实例**：再双击一次启动器 → 不开第二个，而是把已运行的主界面唤到前台（QLocalServer IPC）。
5. 切一下暗色主题。

**必须吃透的 3 个概念**
- **托盘驻留**：关窗 ≠ 退出；server 角色承载整个房间，必须常驻。
- **单实例 IPC**：QLocalServer 命名管道，第二个进程发一条 `show` 消息后退出。
- **热更新 Token**：旧 Token 立即 403，已加入的好友需新 Token 重新加入。

**可能被问**
- "为什么关窗不退出？"→ 关了全房间断线；托盘是房间服务的载体。
- "Qt 用的什么？"→ PyQt5 + qfluentwidgets，fluent 风格，零额外重依赖。

## 组员 C —— 同意流、文件空间安全与测试发行

**开场白（30 秒）**
"我讲两块：Fungi 怎么在'AI 自由协作'和'用户地盘神圣'之间划边界；以及项目的质量保障与发行。"

**演示脚本**
1. **同意流**：主机 A 的 AI 对 B 的文件发起操作 → B 的 WebUI 弹 consent 卡；四个选项：允许 / 禁止 / 自定义输入 / 始终允许。选"自定义输入"回复一句条件同意。
2. **断线重放**：把 B 断网再重连 → 未裁决卡片还在（心跳重放机制）。关键设计："同意就是一条普通消息信封，没有协调服务，所以天然继承消息层的可靠投递。"
3. **文件空间三分区**：
   - `public/`——所有通讯 clone 自由读写（协作区）；
   - `homes/<host>/`——属主写自己家自由，**别人读写都要属主用户同意**；
   - `sessions/`——clone 完全摸不到，只能经本机 clone 代理给用户。
4. **server 端强制**：路径守卫做前缀校验，拒绝 `..` 与绝对路径逃逸——安全边界放 server，因为客户端（AI clone）不可信。
5. **send_file**：字节流 hub 暂存（store-and-forward），接收方同意后落 `inbox/<来源主机>/`，来源可追溯。
6. **质量与发行**：`scripts/check.ps1`（ruff + pytest，267 passed）；GitHub Actions push 即跑 pytest 硬门禁；打 tag 自动出源码 zip + Release（v0.1.0 已发布）；config.json 不入档。

**可能被问**
- "homes 里 AI 写自己家也要同意吗？"→ 属主 clone 不用，防的是**别的**主机。
- "测试怎么跑？"→ 本地 check.ps1；CI Windows runner 跑 pytest，无 Qt 自动跳过 Qt 用例。
